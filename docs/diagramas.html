solventa-frontend-mobile · Android

Cómo viaja el código de tu máquina al teléfono

Lo que deja el primer PR de mobile: devcontainer obligatorio, flavors dev y prod, checks de cada PR, builds de develop y main, pruebas en emuladores y teléfonos reales, seguridad, versionado y rollback. Firebase ya está en los workflows y se saltan solos hasta que existan las cuentas.

1 · Correr el proyecto en local

Todo corre dentro del devcontainer. Fuera solo quedan el emulador y el teléfono, conectados por el servidor adb de tu máquina.

  1. VS Code → Reopen in Container.
  2. Abre el emulador o conecta el teléfono. En una terminal de tu máquina: en Mac adb start-server; en Windows y Linux adb kill-server && adb -a nodaemon server start.
  3. En el contenedor: flutter devices y flutter run (usa dev).
  4. Antes del PR: tool/verificar.sh; el hook de pre-push lo corre solo.

  • Versión: sale de los títulos de los PR (feat sube la menor, fix el parche). El build siempre crece, también en un rollback.
  • Prod: firmado, con R8 y Dart ofuscado. El Release guarda el mapping y los símbolos para leer los errores.
  • Rollback: recompila un tag viejo con un build nuevo, porque Android no deja bajar de versión.

Cada nivel atrapa lo que el anterior no ve. Lo manual queda como evidencia en el repo.

  • Seguridad en cada PR: gitleaks en todo el historial, actionlint, acciones fijadas por SHA y osv-scanner. MobSF corre sobre el APK de develop.
  • Exploratoria: una sesión por sprint con el checklist de 10 puntos. Los hallazgos medios y altos van a Jira.
